Decisions

D1 What is the writing-comments skill built from?

Chosen

  • reference-checker SKILL.md and comment_format.md applied by the session, plus a comment_sections.py command that prints a module's outline and flags dividers off the canonical form

Unchosen

  • reference-only SKILL.md and comment_format.md only; every behavior scenario-tested
  • sibling-agent a dispatch driver and a comment-writer agent per file, like writing-docstrings

Developer decision, 2026-11-24. The divider form is decidable by a command; comment quality is not.

D2 Which divider forms are canonical?

Chosen

  • two-levels major: rule / title (plus optional lines) / rule; minor: `# -- name ---` to the width; every other separator comment is a style flag

Unchosen

  • three-levels the two plus `### ===== NAME ===== ###` as a class-group level
  • any-consistent no canonical form; only mixed styles or widths in one file are flagged

Developer decision, 2026-11-24.

D3 Where does the divider width come from?

Chosen

  • key-88 new key comments.divider_width, default 88

Unchosen

  • reuse-docstrings docstrings.line_length (110)

Developer decision, 2026-11-24. 88 is the width of the issue's full-width rule.

D4 When does the skill act on existing code?

Chosen

  • new-and-touched fires on writing or editing Python; dividers in modules the work creates or on an explicit ask; comments rewritten only in the code being changed; an untouched module is never restructured unasked

Unchosen

  • explicit-only fires only on an explicit ask

Developer decision, 2026-11-24.
