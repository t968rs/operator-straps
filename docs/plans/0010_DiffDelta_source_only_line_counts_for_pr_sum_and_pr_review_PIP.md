## Decisions

- **D1** What do review JSON stats.additions/deletions/files_changed mean once source counts exist? Chosen: `keep-totals` (Keep the full totals; add a stats.source sub-object). Rejected: `source-only` (Change them to source-only; move the totals to a sub-object). Developer choice: old and new review JSONs keep one meaning.
- **D2** Where do the skills get their DiffDelta? Chosen: `from-stats` (from_stats over the per-file counts already captured; between() for any two refs). Rejected: `between-only` (Every caller runs between(ref_a, ref_b)), `persisted` (Persist the delta in the skeleton and plan.json). Developer choice (approach A): no extra git read, working-tree captures keep their counts.
- **D3** Which pr-sum format shows the source versus machine-generated counts? Chosen: `delta-table` (Source / Machine-generated / Total table, shown when any file is excluded). Rejected: `source-header` (Header leads with the source delta; a one-line note names excluded files), `short-note` (The current header and over-half trigger, with a tighter note). Developer choice for issue 234.
- **D4** How does PrFile.artifact reach the project exclusion patterns? Chosen: `active-cache` (diff_delta.active_patterns(): the active project patterns, cached on the exclusions file path, mtime and size). Rejected: `explicit` (Thread a patterns argument through new_draft, draft_problems, render_summary and run_diff). Every pr-sum call site already runs under an activated config; the property keeps its callers.
- **D5** What does pr-sum do when the configured exclusions file is missing? Chosen: `harness-fallback` (Use the harness output patterns alone). Rejected: `raise` (Fail the capture with a problem line). A summary never fails on a review-only file; pr-review keeps its strict exclusion_patterns.
