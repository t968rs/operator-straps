D1 How the work splits between the mod, the widget and the harness (spec Approaches).

Chosen

  • A Mod renders the line; the ccstatusline widget only prints a file

Unchosen

  • B Mod stores refs; a Python widget renders
  • C No mod; plan.py writes refs and the widget matches each repaint

Developer's choice: no code or plugin path in the widget, one file read per repaint.

D2 When does a plan qualify for the current branch (spec Section 2)?

Chosen

  • either plan.branch equals the branch, or plan.base_commit equals git merge-base HEAD <plan.base_branch>

Unchosen

  • branch-only only plan.branch equals the branch

Developer: two ways to qualify; every qualifying plan shows its own link.

D3 When does a plan link leave the banner (spec Section 2)?

Chosen

  • archive an archive/<stem>/ tag exists for the plan

Unchosen

  • done the plan has no open items

Developer: plan.py archive is the trigger; checked by tag since archive writes no file.

D4 Where the ccstatusline widget lives (spec Section 4).

Chosen

  • project the project's .claude/ccstatusline.json, written by setup-statusline

Unchosen

  • user the user's ~/.config/ccstatusline/settings.json

Developer: the plans folder and state_dir are per-project config.

D5 Where the automatic refs come from (spec Section 1).

Chosen

  • field a structured refs field on the ActionPlan, set by plan.py new --refs

Unchosen

  • prose issue numbers scraped from item prose

Developer: a distinct field; prose names issues a plan only mentions.

D6 Which files hold the override and the rendered line (spec Section 2 names one refs.json).

Chosen

  • split overrides.json written only by the harness command; line.txt written only by the mod

Unchosen

  • one one refs.json both sides write

Plan-level: one writer per file, so a mod rescan never clobbers an override written between its read and write; the plan matches are recomputed on each scan and need no file.

D7 When a TODO id's catalog issues are filled in (spec Section 1 says when the line is built).

Chosen

  • write at write time, by plan.py new and the working command (Python reads the catalog)

Unchosen

  • render at render time, by the mod reading the catalog

Plan-level: the harness already resolves todo.folder and the catalog; the mod then never reads the catalog or copies its config.

D8 How the plan link renders in ccstatusline.

Chosen

  • osc8 an OSC 8 hyperlink, visible text 'plan NNNN', target the page's file:/// URL; widget preserveColors true

Unchosen

  • path the bare page path

ccstatusline 2.2.32 keeps escapes when preserveColors is true and draws OSC 8 links itself (renderOsc8Link, its git-pr widget); a live check confirms it on screen (TASK-8).
